# Протокол имитационного эксперимента

Сравниваются Count, QPS, Work и Cost. Это модель одноканальных очередей узлов, а не запуск CockroachDB, Shard Manager или другой СУБД. Код и синтетические данные позволяют воспроизвести числа статьи.

## Запуск

Python 3.9+, внешних библиотек для расчёта и анализа не требуется. Опубликованная серия рассчитана Python 3.9.6 на macOS arm64. Время выполнения скрипта не является метрикой эксперимента.

Из корня репозитория:

```sh
python3 -m unittest discover -s experiment -p 'test_*.py' -v
python3 experiment/run.py --out experiment/results
python3 experiment/analyze.py experiment/results
```

Повторный запуск перезаписывает результаты. Для отдельной проверки можно указать `--out other-results`; `--seed-count 1` запускает один seed на профиль. Эффективная конфигурация сохраняется вместе с результатами.

Для перерисовки иллюстрации и таблицы статьи используется отдельное окружение Python 3.12 с matplotlib:

```sh
python3 -m pip install -r experiment/requirements-plots.txt
python3 experiment/make_figure.py
```

## Постановка

Конфигурация находится в `config.json`: восемь узлов, 24 сегмента, три реплики. У каждой группы одна управляющая реплика. Чтение выполняется на ней; запись создаёт операцию на всех трёх копиях. Обслуживание занимает 4 мс для чтения, 12 мс для записи на управляющей копии и 8 мс на ведомой, делённые на относительную производительность узла.

Начальное циклическое размещение имеет по девять реплик и три управляющие роли на узел. Доли записей и размеры сегментов меняются с seed. Размеры выбираются из 64, 128, 256 и 512 МиБ, доли записей — из интервала 0,05–0,6. Ёмкость узла — удвоенный средний объём реплик с округлением вверх до 64 МиБ.

Профили:

- `uniform`: равные интенсивности сегментов, одинаковые узлы.
- `zipf`: ранги запросов распределены по Zipf с показателем 1,1.
- `shift`: ранги горячих сегментов меняются каждые два окна.
- `heterogeneous`: те же входы, что в `zipf`, но скорости узлов равномерно расположены от 0,65 до 1,35; среднее равно единице.

Суммарный поток — 300 внешних запросов в секунду. Для каждого профиля используются seed 0–11, шесть окон и четыре стратегии: 192 траектории, 1152 окна работы стратегий. У каждого окна пять секунд разогрева и 15 секунд измерений. Размещение наследуется, очередь каждого окна запускается заново.

Генерация входных запросов отделена от балансировки. Все стратегии получают одинаковый список `(время, сегмент, запись/чтение)` для одного профиля, seed и окна. В `inputs.json` находятся параметры генерации и контрольные суммы трасс. Трассы воспроизводятся `request_trace`; сохранять каждое событие для этого не требуется.

## Стратегии и ограничения

- Count минимизирует нормированные отклонения числа копий и управляющих ролей. В начальном размещении они уже равны, поэтому Count не выполняет переносов.
- QPS балансирует число узловых операций, включая операции на ведомых репликах. Он не различает стоимость чтения и записи и не учитывает скорости узлов.
- Work учитывает ожидаемую занятость узлов и штраф приближения к насыщению.
- Cost использует тот же критерий Work и дополнительно штрафует копирование и смену управляющей роли.

У всех одинаковы множество действий, ограничения и лимит в 12 действий на окно. Копирование ограничено 512 МиБ. Смена роли между уже существующими копиями не копирует полный сегмент; это не означает нулевого протокольного времени. Перенос управляющей копии меняет и размещение, и управляющую роль. Полные размеры сегментов учитываются при каждом переносе, в том числе повторном.

Для Work и Cost вес штрафа насыщения равен 0,05, минимальное улучшение — 0,001. У Work оба штрафа действий нулевые. У Cost вес копирования равен 0,1, смены роли — 0,002. Абляция сравнивает совместное добавление двух штрафов и не разделяет их индивидуальные эффекты. Коэффициенты фиксированы в конфигурации; результаты не означают, что эти значения оптимальны.

## Метрики и статистика

`mean_ms` — время узловой операции от поступления до завершения, включая FCFS-ожидание. Операции записи на разных репликах учитываются отдельно. Сетевая задержка, ожидание кворума и полная клиентская транзакция не измеряются.

Операции, поступившие в измеряемом интервале, учитываются и при завершении после его границы. У перегруженного узла это результат конечного окна, а не стационарная задержка.

Среднее траектории взвешивается по числу операций в шести окнах. `p95_window_mean_ms` и `p99_window_mean_ms` — средние перцентилей отдельных окон, а не перцентили объединённой выборки. Внутри окна используется ближайший ранг `ceil(p*n)`. `rho_std` усредняется по окнам, `rho_max` траектории является максимумом по окнам. В `summary.csv` для него затем указано среднее максимумов по seed. `overloaded_windows` суммирует окна с хотя бы одним `rho >= 1`.

Копирование суммируется за шесть окон, а затем усредняется по seed. Нельзя сравнивать этот объём с лимитом одного окна 512 МиБ без учёта числа окон.

Bootstrap использует 10 000 повторных выборок и независимую единицу seed. Для сравнений сохраняется пара Cost/базовая стратегия одного seed. В `paired.csv` разность имеет направление **Cost минус базовая стратегия**. Процентное изменение — отношение разности средних к среднему базовой стратегии. Доверительные интервалы относятся к этой конфигурации генератора; они не подтверждают внешнюю валидность модели.

## Границы модели

Нет отказов узлов, изменения числа реплик, сети, дискового ввода-вывода, ошибок оценки интенсивностей и временной конкуренции миграции с запросами. Перемещения считаются завершёнными перед измерением. Ограничения проверяются на конечных размещениях каждого действия. Сохранение доступности в реальном протоколе перехода между конфигурациями Raft здесь не моделируется.

В серии получено ноль нарушений реализованных ограничений размещения, ёмкости и бюджета. Это свойство стенда, а не свидетельство безопасности промышленного протокола. Базовые эвристики не представляют все возможные реализации Count или QPS. Локальный поиск не гарантирует глобальный оптимум.
